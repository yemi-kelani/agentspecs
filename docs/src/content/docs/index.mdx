## What a spec packet is

[Judgment] A spec packet is a folder of plain files that carries one medium-to-hard coding task from a clarified goal to verified slices. It sits in the repository beside the code it changes, so people and agents review it like any other file.

```text
packets/<task-id>/
├── plan.md            always loaded: goal, assumptions, grounding, slices, decisions
├── acceptance/        checks written before code; the implementer never edits them
├── slices/NN-name.md  one brief per slice: one behavior, one check
├── state.json         slice status; only the verifier sets passes
└── handoffs/NN.md     what changed, raw check output, dead ends
```

[Judgment] A slice is one verifiable behavior, not a workflow stage. Count and size follow verification boundaries, not a fixed number of phases.

## What the evidence says, and what it does not

[Evidence] Each part of the packet traces to cited rows in the [Ledger](/evidence/ledger/), and those rows differ in how much they show. A peer-reviewed study found that giving agents a standard plan beat no plan for every model tested ([R9](/evidence/ledger/#r9)). A benchmark of impossible tasks found frontier models cheating on tests they could edit ([R18](/evidence/ledger/#r18)). Other parts rest on single preprints, vendor posts or practitioner reports; each row says which, in its caveat.

[Judgment] **The packet as a whole has not been tested head to head** against a single plan file, another spec format or no structure at all. [Open questions](/evidence/open-questions/) describes that experiment and how to run it.

## How it runs

<Steps>

1. **Clarify and ground.** [Proposal] A person confirms the assumptions, and the plan records real paths, APIs and commands from the repository, because many agent runs fail at clarification and planning ([R10](/evidence/ledger/#r10)).

2. **Acceptance first.** [Proposal] Checks are written or reviewed by a person before code exists, and a hold-out subset stays with the verifier ([R15](/evidence/ledger/#r15), [R18](/evidence/ledger/#r18)).

3. **Review the plan.** [Judgment] Someone other than the plan's author confirms that every slice maps to a check and no check contradicts the goal.

4. **One slice per session.** [Proposal] The orchestrator injects plan.md and one slice brief into a fresh session and re-injects them periodically ([R9a](/evidence/ledger/#r9a), [R3c](/evidence/ledger/#r3c)).

5. **Separate verification.** [Proposal] A different session runs the checks and hold-outs and is the only one that sets `passes` ([R18](/evidence/ledger/#r18), [R95](/evidence/ledger/#r95)).

6. **Hand off.** [Proposal] The handoff keeps raw check output and dead ends and retires facts that stopped being true ([R22a](/evidence/ledger/#r22a), [R24](/evidence/ledger/#r24)).

</Steps>

[Judgment] [How it works](/approach/how-it-works/) tells the whole loop, including the dispute and replan rules.

## Where it fits

[Judgment] The packet needs no runtime or plugin. Any coding agent that can read and write files can follow one, and a person can act as orchestrator or verifier. Repository-wide rules stay in a short [AGENTS.md](https://agents.md/); reusable procedures can stay in [Agent Skills](https://agentskills.io/specification).

Agent Specs is an independent project. It is not affiliated with, or endorsed by, the AGENTS.md or Agent Skills projects or any agent vendor. Ideas borrowed from other formats are credited where they are used and on [Credits](/credits/).
