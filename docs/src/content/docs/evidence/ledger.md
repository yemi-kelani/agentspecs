## Conflicts

Rows that point different ways. Each conflict names its rows and says what the disagreement does and does not cover.

### C1: Do context files raise or lower cost?

Rows: [R1a](#r1a), [R2](#r2).

R1a found that context files raised inference cost by about 20% and added agent steps; R2 found that an AGENTS.md lowered median runtime by 28.6% and median output tokens by 16.6%. The studies measure different things (mean dollar cost and steps across four agents against median runtime and token counts for one agent), and R2 found no change in total tokens, so its result does not contradict R1a on cost. The real tension is output tokens: reasoning tokens rose by up to 22% in R1 and output tokens fell in R2. R2 did not measure correctness. Neither study tested task specs.

### C2: Do file size and position matter?

Rows: [R3](#r3), [R3a](#r3a), [R4](#r4), [R6](#r6), [R5d](#r5d).

R3 found no effect of instruction-file length (25 to 500 lines) and R3a no effect of where one rule sat in the file, while R6 found a U-shape in which information in the middle of the input was used worst, and R4 found accuracy falling as the number of instructions grew. R3 against R4 is not a direct conflict: R3 varied filler around one scored rule, R4 varied how many rules were scored at once. R3a against R6 is a partial tension, since R6 saw U-shapes at input sizes close to R3a’s 2-3k-token file. Possible reasons include a retrieval question against an always-on rule, position within a file against position within the whole prompt, 2023 against 2026 models, and R3a’s detection limit of about 6 points. R5d also found no position effect in its retrieval task.

### C3: Does always-loaded context help?

Rows: [R1](#r1), [R20](#r20).

R1 found that always-loaded context files gave no general gain in task success, while R20 found that an always-loaded docs index in AGENTS.md reached a 100% pass rate where an on-demand skill reached 53%. R20 tested framework APIs absent from the model’s training data and does not disclose its sample size; R1 tested ordinary Python repositories. The two are compatible if context helps only when it carries facts the model cannot get elsewhere.

### CN1: Does an embedding index beat agentic grep-style search for finding code?

Rows: [R165](#r165), [R166](#r166), [R172](#r172), [R175](#r175), [R177](#r177).

A code question-answering study (R165) found a vector-index agent beat a subagent-exploration agent, and Cursor's 2025 post (R175) found semantic search added accuracy, while SWE-Explore (R177) found agentic exploration far above a weak static-embedding retriever and the memory study (R166) found grep ahead of vectors on chat text. The tasks (question answering, localisation, memory), the embedding models and what counts as agentic search differ across these rows, so none of them is a direct head-to-head on patching real repositories. R175 is vendor-run on an unreleased benchmark, R165's pooled gap is driven mostly by one model, and R166 is not about code.

### CN2: Did the vendor's own evidence for semantic search hold up?

Rows: [R175](#r175), [R176a](#r176a).

Cursor's November 2025 post reports gains from semantic search; its current documentation describes an Instant Grep design with no stored embeddings. The documentation gives no measurements, so it does not show the earlier result was wrong, only that the product changed.

### CN3: Does repository size lower agent success?

Rows: [R167](#r167), [R169](#r169), [R170](#r170), [R165c](#r165c), [R170a](#r170a).

Three benchmarks report lower success on larger repositories (R167 translation, R169 features, R170 issue fixing), but size is read from figures or small bins (R167's bin counts differ between its text and its table) and is confounded with project and task difficulty. One study found no significant size trend in cost overhead (R165c, 15 repositories), and R170a shows simpler, smaller repositories with lower success. None varies size while holding the repository and task fixed.

### CN4: Do code graphs and structure-aware tools raise agent success?

Rows: [R160](#r160), [R161](#r161), [R163](#r163), [R162](#r162), [R162a](#r162a), [R163a](#r163a).

RepoGraph, LocAgent and ARISE report gains on SWE-bench Lite with GPT-4 and GPT-4o, Claude-3.5 and a 32B open model (R160, R161, R163); LocAgent's gain is in localisation accuracy, not resolve rate. CodexGraph only matched an AST-search baseline with GPT-4o and lost with weaker models (R162, R162a), and ARISE gained almost nothing with a stronger model and lost on AutoCodeRover (R163a). The gains are measured on one benchmark, mostly in single runs, and shrink or vanish in several settings.

### CS1: Does handing a model retrieved pieces instead of the whole context help on code tasks?

Rows: [R200b](#r200b), [R200c](#r200c).

One benchmark gave Claude 3.5 Sonnet a RAG pipeline in place of the full repository prompt. On issue fixing it solved 23, 23, 22, 21, 16 and 22 percent across the 32K to 1M brackets, against 29, 19, 15 and 3 percent with the full context at 32K to 256K (no full-context result beyond 256K), so retrieval was worse at 32K and better only from 64K on. On code question answering the same pipeline scored 12.8 to 31.2 percent, which the authors call comparable to random guessing. One model, one retrieval setup that the authors call a narrow view of RAG, and no agent choosing its own reads.

### CS2: Does loading a short index first and fetching detail on demand help agents?

Rows: [R20](#r20), [R203a](#r203a), [R204a](#r204a), [R204](#r204).

Vercel's eval (undisclosed sample size, vendor-run) found a compressed docs index always loaded in AGENTS.md passed 100 percent against 53 percent for a skill left to the agent, with the skill never invoked in 56 percent of cases. A controlled long-document study found a flat skill pack added nothing for a strong agent on a single book but raised English open QA from 0.26 to 0.46 across a 20-book library. A preregistered wiki study found a capable agent never loaded the large index in its pilot, yet the retrofitted version cost 30 to 34 percent less per answer, a saving the author attributes to more targeted access rather than shown to be caused by it. The tasks differ (framework docs, books, a wiki), none tests a plan file pointing to step files, and only the wiki study is preregistered.

### CT1: Do repository instruction files measurably change what agents produce?

Rows: [R183](#r183), [R191](#r191).

The AI IDE rules study sees compliance of project artifacts with a rule rise from 49.14% to 72.13% across 160 rule-update events (before and after, scored by an LLM judge, no control group). The two-agent ablation sees no significant change in gold-test pass rates between no context and a full AGENTS.md (15 Claude Code and 17 Codex tasks from 3 repositories; it can exclude only effects larger than about 10 to 15 points). They measure different outcomes (following a rule against solving the task), cover different tools, and both are preprints, so the pair does not settle whether files help.

### CV1: Do tests help an agent resolve repository issues?

Rows: [R15](#r15), [R15a](#r15a), [R231](#r231).

R15 and R15a show a test-driven agent workflow resolving most SWE-bench tasks when given the benchmark's human-written tests and doing worse when it wrote its own; R231 finds that prompts that made agents write more or fewer exploratory tests on SWE-bench Verified did not significantly change resolution (four models, 500 tasks, all p > 0.05). They do not test the same thing: R15 uses the tests as a gate the fix must pass, R231 changes only how often an agent writes its own scratch tests, with no gate. Neither compares test-first with test-after or with no tests, and a non-significant result on 500 tasks is not proof of no effect.

### CV2: Can model-written tests tell correct code from incorrect code?

Rows: [R223a](#r223a), [R225a](#r225a), [R226](#r226), [R229](#r229), [R230](#r230).

R223a, R225a and R226 find that model-written tests can filter or rank candidate solutions: filtering reaches 47.8% precision (R223a) and 65-92% (R225a) and CodeT ranking raises pass@1 on function-level problems (R226). R229 and R230 find that tests written from buggy code sometimes assert its behaviour: R229 measured 3.84% of tests passing the buggy code but failing the fix versus 0.46% from fixed code, and R230 found 59.6% and 68.1% of the tests kept by two tools did so on a set of student programs. These cover different test sources: tests written from an issue or problem statement versus tests written from the code under test. The filters also discard most correct fixes (about 80% at 20% recall in R223a, 59-70% in R225a), so none shows model-written tests are a reliable oracle.

### CV3: Does asking an agent to follow TDD help?

Rows: [R17](#r17), [R220](#r220), [R221](#r221).

R17 found that a TDD prompt without a map of affected tests raised regressions (one open-weight model, 100 instances, one run), while R220 and R221 found function-level gains when tests were supplied in the prompt (R220 on thousands of MBPP, HumanEval and CodeChef problems; R221 on MBPP with simulated feedback). R17 is repository-level and about prompting a TDD procedure; R220 and R221 are function-level and only supply tests. No row compares TDD prompting with its absence on repository tasks while controlling test quality.

- <span id="r129"></span>**R129** · Willison's 'lethal trifecta' is an agent that combines access to private data, exposure to untrusted content and the ability to communicate externally, which lets injected instructions exfiltrate data; he sees avoiding that combination as the only safe approach. Source: [The lethal trifecta for AI agents: private data, untrusted content, and external communication](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (simonwillison.net). Verified 2026-10-09. Quote: “avoid that lethal trifecta combination entirely”. Caveat: Threat-model framing by a practitioner, not an empirical study; it describes when exfiltration becomes possible, not how often attacks succeed. `c-willison-trifecta`

## How tools and formats work

- <span id="r7c"></span>**R7c** · Böckeler reports that Tessl, then in private beta, was the only one of the three tools explicitly aiming at spec-anchored development and exploring spec-as-source, mapping one spec to one code file and marking generated code as not to be edited, though repeated generation from the same spec was non-deterministic. Source: [Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) (martinfowler.com). Verified 2026-10-22. Locator: Tessl section. Caveat: Based on a private-beta version in September 2025 as observed by one author; the non-determinism note applies to Tessl only. `c-bockeler-tessl`
- <span id="r21"></span>**R21** · The Agent Skills spec, Anthropic's authoring guide and the Claude Code docs all advise keeping the SKILL.md body under 500 lines and moving detailed material into separate files. Sources: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com); [Specification](https://agentskills.io/specification) (agentskills.io); [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com). Verified 2026-10-22. Quote: “Keep SKILL.md body under 500 lines for optimal performance” (Authoring guide, structure section). Caveat: This is a guideline. No source publishes a measurement showing that 500 lines is a threshold. `a-skill-body-500`
- <span id="r21a"></span>**R21a** · The Agent Skills spec and Anthropic’s authoring guide advise linking every reference file directly from SKILL.md (one level deep), because an agent may only preview files reached through nested references. Sources: [Specification](https://agentskills.io/specification) (agentskills.io); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com). Verified 2026-10-22. Locator: Agent Skills spec, file references; Anthropic guide, progressive disclosure. Caveat: Anthropic says partial reads may happen. It does not say they always happen, and it gives no frequency. `a-skill-refs-one-level`
- <span id="r21b"></span>**R21b** · Anthropic recommends a table of contents at the top of any reference file longer than 100 lines, so that a partial read still shows everything the file covers. Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com). Verified 2026-10-22. Caveat: Vendor guidance for Claude; the 100-line trigger is not justified with data. `a-skill-ref-toc`
- <span id="r59"></span>**R59** · Skills load in three tiers: about 100 tokens of name and description per skill at startup, a full SKILL.md body (recommended under 5,000 tokens) when the skill activates, and bundled files only when they are needed. Sources: [Specification](https://agentskills.io/specification) (agentskills.io); [Agent Skills (overview)](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) (platform.claude.com). Verified 2026-10-09. Caveat: These are approximate design budgets, not measured limits. Real metadata cost grows with description length. `a-skill-disclosure-budgets`
- <span id="r61"></span>**R61** · Scripts bundled with a skill can be run without loading their code into context, so only their output costs tokens and the result is repeatable. Sources: [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (anthropic.com); [Agent Skills (overview)](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) (platform.claude.com). Verified 2026-10-09. Caveat: This requires an agent that can execute code. The output still uses context. `a-skill-scripts-deterministic`
- <span id="r62"></span>**R62** · Once an agent decides to activate a skill, it loads the whole SKILL.md file, so longer content belongs in referenced files. Source: [Specification](https://agentskills.io/specification) (agentskills.io). Verified 2026-10-09. Caveat: This describes expected client behavior. Individual agents may implement loading differently. `a-skill-whole-body-loads`
- <span id="r93"></span>**R93** · Anthropic recommends building evaluations before writing much skill content: run representative tasks without the skill, write three scenarios that target the gaps, measure a no-skill baseline, then write minimal instructions and iterate. Sources: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com); [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (anthropic.com). Verified 2026-10-09. Caveat: This is recommended practice, not a measured result. Anthropic notes there is no built-in way to run these evaluations. `a-skill-evals-first`
- <span id="r131"></span>**R131** · In Claude Code, context: fork runs a skill as the prompt of a new subagent that does not see the conversation history, so the skill must be self-contained and contain an explicit task. Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com). Verified 2026-10-09. Caveat: This corrects the prior report's 'forked subagent' wording: despite the name, the subagent does not inherit the conversation. `a-cc-skill-context-fork`
- <span id="r132"></span>**R132** · Claude Code truncates each skill's combined description and when_to_use text at 1,536 characters in its skill listing (a configurable cap), and advises putting the key use case first. Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com). Verified 2026-10-09. Caveat: This is a Claude Code implementation detail that may change by version. Other clients truncate differently or not at all. `a-cc-skill-desc-1536`
- <span id="r133"></span>**R133** · Claude Code adds its own frontmatter fields to the Agent Skills format, including when_to_use, disable-model-invocation, context: fork, agent and paths (glob-scoped activation), and treats every field as optional, while the open spec requires name and description. Sources: [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com); [Specification](https://agentskills.io/specification) (agentskills.io). Verified 2026-10-09. Caveat: Claude.ai uploads and the Skills API accept only the six spec fields and reject any extra key with a hard error, so extensions reduce portability. `a-cc-skill-extensions`
- <span id="r134"></span>**R134** · Claude Code's skill listing has a character budget of 1% of the model's context window. When it overflows, the least-used skills lose their descriptions first, which removes the keywords Claude uses to match them to requests. Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com). Verified 2026-10-09. Caveat: Claude Code only, configurable, and version-dependent. `a-cc-skill-listing-budget`
- <span id="r135"></span>**R135** · In Claude Code an invoked skill's content stays in the conversation on later turns, so each line is a recurring token cost. After compaction, the first 5,000 tokens of each recent skill are re-attached within a combined 25,000-token budget. Source: [Extend Claude with skills](https://code.claude.com/docs/en/skills) (code.claude.com). Verified 2026-10-09. Quote: “every line is a recurring token cost”. Caveat: This is Claude Code behavior. Older skills can be dropped after compaction when many have been invoked. `a-cc-skill-persist`
- <span id="r137"></span>**R137** · Anthropic advises matching how specific instructions are to how fragile the task is: loose text guidance where many approaches work, and exact scripts with few or no parameters where operations are error-prone or must follow a fixed sequence. Source: [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com). Verified 2026-10-09. Caveat: This is a qualitative design rule with no evaluation data behind it. `a-skill-degrees-freedom`
- <span id="r138"></span>**R138** · A skill description must be 1 to 1,024 characters and should say what the skill does and when an agent should use it, with keywords that help an agent match it to tasks. Sources: [Specification](https://agentskills.io/specification) (agentskills.io); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com). Verified 2026-10-09. Caveat: The 1,024 limit is the spec's. Claude Code's listing applies a separate 1,536-character cap to description plus when_to_use. `a-skill-description-limit`
- <span id="r139"></span>**R139** · A skill name must be 1 to 64 characters of lowercase letters, digits and hyphens, cannot start or end with a hyphen or contain two hyphens in a row, and must match its parent directory name. Sources: [Specification](https://agentskills.io/specification) (agentskills.io); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (platform.claude.com). Verified 2026-10-09. Caveat: Anthropic's platform also bans XML tags and the words 'anthropic' and 'claude' in names. The directory-match rule comes from the open spec; Anthropic's best-practices page does not state it. `a-skill-name-rules`
- <span id="r140"></span>**R140** · The optional compatibility field is capped at 500 characters, and the spec marks allowed-tools as experimental, with support varying between agents. Source: [Specification](https://agentskills.io/specification) (agentskills.io). Verified 2026-10-09. Caveat: The spec notes that most skills do not need compatibility. What allowed-tools does depends on the client; in Claude Code it pre-approves tools but restricts none. `a-skill-optional-field-limits`
- <span id="r141"></span>**R141** · The Agent Skills specification requires only two frontmatter fields, name and description; license, compatibility, metadata and allowed-tools are optional. Source: [Specification](https://agentskills.io/specification) (agentskills.io). Verified 2026-10-09. Caveat: This is the open spec. Individual clients can be looser (Claude Code treats every field as optional) or stricter (Anthropic's platform rejects unknown keys). `a-skill-required-fields`
- <span id="r142"></span>**R142** · Anthropic advises writing skill descriptions in the third person, because the description goes into the system prompt and a shifting point of view can cause discovery problems.
